# Security and publication review

Project: **Wazuh EQL Correlation** (`wazuh-eql-correlation`).

The original construction audit was local and offline. Subsequent bounded native execution is recorded in Phase 7B; the [scheduled validation report](verification/scheduled-kibana-validation/REPORT.md) records user-confirmed isolated synthetic scheduled tests of all 14 rules on 5 November 2026. The operator confirms existing production rules and Wazuh configuration were not modified during that validation. This documentation update does not perform service operations or publish the repository. There are no private repository dependencies or runtime Python services.

Use a dedicated least-privilege Elasticsearch ingest identity instead of the historical `elastic` superuser. Scope index privileges to the intended pattern and required write/index-creation operations for the chosen provisioning model. Template management and ILM are disabled in the example; an administrator must preflight mappings and privileges. Avoid broad cluster privileges. Secure readers and rule administrators separately. Credentials belong in protected deployment configuration or a keystore, never tracked examples. Environment secrets may be visible to privileged local processes; protect the host and diagnostic output.

TLS certificate verification is full. Only a CA *path* is tracked, not certificate bytes; no private keys are needed in the repository. Protect the Wazuh alerts file, ACLs, queue, checkpoint and Elasticsearch data as sensitive. Review source IPs, usernames, host identifiers, URLs and paths before sharing evidence. Use labelled synthetic events rather than exporting production payloads.

The historical publication review checked repository publication candidates, not an external host. The current workspace has Git metadata and history; the historical audit is not a fresh scan of the current tree. The repository contains only localhost endpoints and reference service paths, no private address literals, real host/user identifiers, certificate/key material, production event logs or private repository links. The WordPress volume name `web_wp_data` and root-target predicate are supplied detection context, not evidence of an actual host or account compromise. Rule IDs and file paths are intentional source material. CHANGE_ME values are unusable examples. Automated pattern scans and manual review reduce accidental disclosure risk but are not a formal secret-detection guarantee.

Production qualification remains pending for representative Wazuh telemetry, field compatibility, event coverage and detection accuracy. User-confirmed synthetic scheduled alert generation closes the earlier scheduled-alert readiness gap, subject to the PRIV-001 candidate distinction. Historical reproducibility gaps, published PRIV-001 optional join semantics, representative rootcheck path availability and query-window coverage still require review. Agent-only PRIV-001 correlation increases false-positive risk and requires production review. SOC Automation integration, Case publication, remediation and external SOC handoff are not qualification requirements. Source recovery and MAL-001 refinement are complete. A sanitised source-only reference may be reviewed for publication with these limitations explicit; no GitHub publication is authorised or performed. Apache-2.0 covers repository content; review third-party service licensing separately.

Phase 3 finds no remaining source-publication security blocker. The repository is suitable for experimental source publication with the stated limitations.
